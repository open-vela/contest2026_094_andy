# DMA、cache 一致性与中断驱动的数据通路

## 1. 先记住这条经验

**CPU 侧看起来全对（链表、寄存器、缓冲内容都正确），DMA 却读到 0 或读到旧数据 → 几乎一定是 cache 维护问题。**

反面教训：这类现象容易被误判成"中断没来""优先级不对""器件没启动"，于是在中断控制器和电源上浪费大量时间。先用一个小实验排除 cache（把同一段数据用不同的维护方式各搬一次，比较结果），再怀疑别处。

## 2. 描述符环设计

以"外设 → 内存"的采集通路为例，一个可用的最小环：

- 描述符要满足控制器要求的**对齐**（常见 32 字节）；
- 每个描述符的"所有权/传输长度/地址"字段由 CPU 填好，**清理 cache 后**才交给 DMA；
- 两个描述符**双向链接**组成循环，避免 DMA 跑到尾部就停；
- 描述符数组本身也是 DMA 访问的内存，同样要做 cache 维护；
- 上层缓冲用 `kmm_memalign()` 之类保证对齐，不要用普通 `malloc`；
- 缓冲大小与周期数要写在 board 层可调，方便按场景缩放（采集周期、音频帧长）。

双缓冲/多缓冲的意义是"一块在填、一块在处理"；单缓冲很容易在收尾时丢数据或踩到正在被 DMA 写的内存。

## 3. cache 维护：最隐蔽的一类 bug

真实案例（vendor 提供 `csi_dcache_clean_range()`）：

- 该函数的内联汇编里，T-Head 的 cache 指令**把地址寄存器固定写成 `a5`**，但这个约束没有告诉编译器；
- 编译器在循环里用自己的寄存器（`a4`/`a0`）迭代地址，实际执行时 `a5` 里是别的东西；
- 结果：`clean` 维护的是错误的 cache 行，DMA 读到的内存仍是脏/旧内容——**但在 C 代码和寄存器回读上完全看不出来**。

定位方式：
1. 反汇编相关函数，确认循环里"迭代地址的寄存器"和"cache 指令使用的寄存器"是否一致；
2. 对照勘误：这是"函数看起来跑过、参数也对，但效果不存在"的典型。

修法（择一）：
- 在**自己的目录里**重写带约束的实现：把 cache 指令的地址寄存器作为显式约束（如 `"a5"`）绑定，保证编译器把循环地址放进同一个寄存器；
- 或按行手工维护（按 cache line 大小循环），不依赖 vendor 的批量 helper。

验证：**改完必须再反汇编一次**，确认地址确实进了被约束的寄存器；然后用数据面结果（采集内容、文件长度、CRC）确认。

其它要点：
- clean（写回）与 invalidate（作废）方向不能搞反：DMA 要读内存 → 先 clean；DMA 写完后 CPU 要读 → 先 invalidate；
- 有些平台没有"按地址精确 clean"的能力，只有整片 flush。此时要注意 flush 的粒度与副作用（例如刷新整块 framebuffer 会带来闪烁或额外带宽）；
- 通用的 "clean range" 名字不代表它能用——**看反汇编，不看函数名**。

## 4. 启动顺序与硬件握手

外设的"使能序列"顺序错了，表现往往是"状态寄存器在动、数据通路不动"：

- 典型正确顺序（以某 DMA 采集外设为例，需按手册核对）：
  **装载 DMA 任务 → flush FIFO → 打开全局接收 → 配置数据移位 → 最后打开请求（DRQ）**；
- 反例：先打开 DRQ 再装载任务 → 控制器发出 `ADDRESS_REQUEST` 类错误，数据通路始终不工作；
- 出错时读回硬件状态（task/former/src 等字段）比只看返回值有效得多；`state=3 error=5` 这类码要对着手册翻译；
- 若控制器支持"单次触发/循环模式"，先确认模式位，再查触发方式（寄存器触发 vs 外部请求）。

## 5. 完成、尾缓冲与收尾顺序

- **中断里判定完成后，不要立刻清理缓冲**：先把外设停下来 / 把尚在 DMA 手里的缓冲要回来，再向框架报告 COMPLETE；
- 否则残留在 DMA 手里的缓冲可能被复用时踩坏内存（出现过收尾阶段 `tail` 指针变 `0x8` 的崩溃）；
- 上层框架的"停止/暂停"回调必须真的有实现：某些 vendor 驱动里 `pause/resume` 是**空 ops**，调用后会以 `epc=0` 跳空指针的形式崩溃；
- 关闭设备（close）路径要能重复调用且不泄漏（工作队列/定时器/信号量/缓冲都要成对释放）。

## 6. 中断与下半部

- 中断上下文只做最少的事：读状态、清中断、把工作交给 worker/work queue。不要在里面做总线 I/O 或长耗时处理；
- 不要从 ISR 直接唤醒调度器去做重活；用 work queue 更安全；
- IRQ 号有两层：**控制器的原始源号**和**内核 IRQ 号**。映射错的表现是"中断永远不进"或"进了别的处理函数"。挂接顺序：`irq_attach()` → `up_enable_irq()`；
- **不要和上层轮询抢同一个状态位**：中断处理里清掉某个"完成/就绪"标志，而上层同时在轮询该位，就会出现偶发超时（谁先抢到决定成败）。要明确该状态位由谁消费：要么纯轮询且不注册该中断，要么中断处理后把结果交给上层——不要两边都读/清。中断最好按控制器用途分开使能，避免"为了一个功能把整组中断都打开"；
- 记录并暴露计数器（中断次数、就绪帧数、错误数），这是判断"中断真的来了"的唯一可靠方式，比"看起来有数据"强。

## 7. 验证 DMA 通路的可观察证据

- 搬运内容：把缓冲内容打印/落盘，检查长度与采样/帧数是否匹配预期；
- 校验：同一段数据用 CPU 读取与 DMA 搬运的结果做 CRC 比较；
- 计数器：`irq > 0`、就绪帧数、错误计数；
- 反汇编：确认 cache 维护指令的地址寄存器正确（这是"修好了没有"的直接证据）；
- 压力与重复：连续跑数秒/多次，并在中途 reset 一次，确认不会只在第一次成功。

## 8. 排查清单

- [ ] 描述符与缓冲满足对齐要求，分配时就用对齐分配器
- [ ] 描述符链双向闭合，长度/所有权限位正确
- [ ] 交付 DMA 前做过 clean；DMA 写完后 CPU 读取前做过 invalidate
- [ ] 反汇编确认 cache 维护函数真正作用在正确的地址上
- [ ] 外设使能序列按手册顺序（先装任务，最后开请求）
- [ ] 中断里只做最少工作，重活交给 worker
- [ ] IRQ 原始源号与内核 IRQ 号的映射验证过
- [ ] 完成路径先停外设、归还缓冲，再报告 COMPLETE
- [ ] stop/pause/resume 回调有实现，且可重复调用
- [ ] 有 irq/帧数/错误计数可供观察
- [ ] 连续运行与复位后重复都通过
