## 1. 一外设一命令一 README

每接入一个外设，同时交付三样东西：

1. **驱动/lower half**：接到标准框架上（`register_*`），产生一个设备节点；
2. **测试命令**：`app/<name>/` 下一个 NSH 命令，能覆盖主要数据路径；
3. **README**：功能目标 / 依赖模块 / 测试步骤 / 预期结果 / 实测结果 / 已知限制。

为什么强制 README：几个星期后，唯一能说明"这个外设当时怎么验、验到什么程度"的就是它。只写在聊天记录里等于没写。
`scripts/validate_stage.sh <repo> S4` 会检查每个 app 是否有 README——缺一个就 FAIL。

命令本身的要求：
- 参数有默认值，非法输入给出范围提示（例如时长 1–300 秒、频率 100–10000 Hz）；
- 结束时打印明确的 `PASS`/`FAIL`；
- **所有退出路径都释放资源**（停 PWM、停 DMA、恢复被借用的 IRQ、关闭设备）；
- 破坏性测试要有显式确认参数（例如复位类测试要 `confirm`）。

## 2. 判定标准必须可观察

避免"看起来正常"。用能客观判定的标准：

| 类型 | 好的判定标准 | 不好的标准 |
|------|--------------|------------|
| 存储读 | 同一区间读两次 CRC32 一致；重启后文件仍在 | "读出来了" |
| 存储写 | 写入 → 复位 → 读回校验 | "写成功" |
| 卡/文件系统 | 挂载点存在、容量/剩余空间合理、写读一致 | "mount 没报错" |
| 触摸 | DOWN/MOVE/UP 事件序列完整、坐标范围覆盖四角、`irq > 0` | "能点" |
| 按键 | 按下/抬起各计数 1 次、原始值合理 | "有反应" |
| 输入设备 | 关闭日志里 `irq > 0`、`ready_frames > 0` | "节点存在" |
| 显示 | 色条顺序正确、分辨率与像素格式符合预期 | "屏幕亮了" |
| 音频 | 生成合法 WAV（文件头 + 时长 + 采样率正确）、采播回环正常 | "有声音" |
| 网络 | DHCP 拿到地址 → ping 通 → HTTP 请求成功 | "网卡注册了" |
| DMA | 搬运结果校验通过（内容+长度），不是只看寄存器状态 | "DMA 完成了" |

原则：**能自动判定的就不要靠肉眼**；必须靠肉眼的（显示/声音）要在 README 里写清"预期看到什么"。

## 3. 证据等级与声明纪律

沿用 `stages_and_gates.md` 的 6 级证据（`none/build/pack/boot/device/data`）。对外描述时：

- `build`/`pack` → 只能说"编译/打包链路已通"；
- `device` → "设备节点已出现/框架已注册"；
- `data` → 才能说"功能已实现并通过实机验证"。

常见过度声明（要主动避免）：
- 拿构建日志当运行证据；
- 拿"节点存在"当"数据正确"；
- 把一次偶然成功当成稳定通过（至少重复几次，包括复位后的重复）；
- 把参考实现/官方文档的行为当成自己已经实现的行为；
- **把"注册/初始化 API 返回成功"当成"设备可用"**：某些 API 在内部失败时仍返回成功，节点并不存在。判定要以"节点可访问并能完成一次数据面操作"为准；
- **把"链接成功"当成"能启动"**：链接成功只说明放进去了，运行时可能因为堆不足/内存布局冲突起不来。要看运行时堆边界（`_sheap`/`_eheap`）与最小堆断言。

反过来，**不确定的结论要标注不确定**：例如"怀疑是上下文保存被污染，尚未定论"。这比一个错误结论有价值得多。

## 4. 回归清单模板

每个外设一行，作为每次改动的回归依据：

```text
设备节点/能力 | 验证命令                          | 判定标准
-------------|-----------------------------------|-----------------------------------------
/dev/xxx     | xxx_test info                     | 识别/几何/分区信息正确
/dev/xxx     | xxx_test read/verify              | 双读 CRC32 一致
/dev/xxx     | xxx_test write → reboot → check   | 掉电后数据保持
/dev/input0  | getevent -t                       | DOWN/MOVE/UP 完整，irq > 0
/dev/fb0     | fb_test                           | 分辨率/格式/图案正确
eth0         | ifconfig → ping → webclient       | 取址、ICMP、HTTP 均成功
```

改动底层（时钟、中断、DMA、cache、链接脚本、defconfig）之后，**至少回归一遍清单前半段**（串口、调度、存储），确认没有把地基弄坏。

## 5. 文档层级

| 位置 | 内容 |
|------|------|
| 仓根 `README.md` | 作品说明：是什么、怎么编译/烧录/运行、能力清单与验证结果、AI 使用说明 |
| 板级 README | 板级细节：构建/打包命令、烧录步骤、引脚与外设映射、每项验证的预期输出 |
| `app/<name>/README.md` | 该测试命令的用法与判定标准 |
| 源码注释 | 只写"为什么"（尤其与参考实现不一致的地方、绕过厂商 bug 的地方） |

板级 README 建议包含"构建 → 打包 → 烧录 → 逐项验证"的完整可复现路径，让评委/同事能照着走一遍。

## 6. 交付物清单

- [ ] 代码（按 chip/board/app 分层，构建清单一致）
- [ ] 可烧录镜像 + 构建/打包命令（记录哈希与入口地址）
- [ ] 每外设的测试命令 + README
- [ ] 回归清单（设备节点 ↔ 命令 ↔ 判定标准）
- [ ] AI Coding 日志（按赛事规范导出，一人一目录 + manifest）
- [ ] 演示材料（视频/PPT/现场 Demo 脚本）
- [ ] 已知限制与未完成项（诚实列出，并说明后续计划）

## 7. 提交与协作粒度

- **按外设粒度提交**，提交信息写清"做了什么 + 怎么验的"（例：`spinor: QSPI0 + MTD + LittleFS /data mount`）。不要把多个外设揉成一次"almost ready"提交，出问题无法二分定位。
- 每个阶段结束打一个可回退的点。
- 改动公共仓库时走 fork + PR，不直接改生产目录。
- 建议维护一份"当前状态"表（哪个外设到哪个证据等级），避免口头进度与仓库实际脱节。

## 8. 收口流程（发版/提交前）

按固定顺序走一遍，任何一步失败就停下修：

```text
1. 干净全量构建（删掉构建输出目录，不用增量）
2. 检查产物：size / readelf 入口地址 / 是否与链接脚本和打包描述一致
3. 拷贝成打包脚本要求的文件名
4. 打包，确认镜像重新生成（时间戳变化）
5. 计算镜像 SHA256，回填到 README
6. 烧录到板子，按回归清单逐项验收
```

要点：
- **完成判据是"板上验收通过"，不是"链接成功"**。链接成功只到 `build` 证据等级。
- 验收完成后再精简 defconfig（关掉不必要的一次性测试应用以省 Flash/RAM），但**保留被列为红线的能力**（网络、自动挂载、UI、录音等演示必需项），并在 README 里说明保留了哪些。
- 收口时同步更新 README：能力清单 + 每项的证据等级 + 已知限制 + 复现步骤。
- 把"最后验证过的镜像哈希"写进文档，避免演示时拿错镜像。

## 9. 与 AI 协作的纪律（本项目经验）

- 提问时**贴原始证据**：完整日志行、真实 errno、反汇编片段、寄存器回读值。不要只描述"不行"。
- 主动纠正 AI 的结论：当用户/同事给出更准确的数字（例如"这个写入量恰好等于分区剩余空间"）时，应以该证据重新推理。
- 要求 AI **明说方向错了**：结论被推翻时，写清"原判断错了、错在哪、新证据是什么"，而不是悄悄换方向。
- 诊断代码的生命周期要有人负责：谁加的插桩，结论确认后由谁移除并复测。
- 每次定位到根因，**顺手把对应的验证命令写进 README**，让结论可复现、可回归。
